## 1. Purpose and why

v0.2 makes the framework faster to deliver with, without lowering the quality bar. v0.1's delivery showed where the time went: tool gaps that forced hand work on every task (findings that could not reach `closed`, `loopstats` refusing inherited findings, briefs with empty sections passing the dispatch check), rules that agents broke because nothing gated them, record kinds written free-form before their schema existed, hand-written handoffs that failed their schema, findings that arrived one class member per round, local suite and mutation runs that CI could have carried, and no measurement of where agent time went (inventory section 1; LS rows A2, A3, C1, C2).

The owner's failure criteria for v0.2 (notes, "Success and failure"): "if it takes as long as v0.1 did, if it made no improvements to delivery time while maintaining quality standards, if i have to change the spec halfway through due to improper planning that wasn't thorough enough."

So v0.2 has two jobs: remove what slowed v0.1 down (stages B and F first), and be planned completely enough that the spec does not change during the build. Every new feature is discussed and planned properly with the owner before it enters the spec (notes, "Success and failure"); this spec adds nothing the notes do not hold.

## 3. Success measures

- Delivery time. Target: under one week from the start of v0.2 work to the v0.2 tag, excluding usage-limit stops, with an extra week of leeway. Owner 2026-11-26: "v0.2 will only start after v0.1 so if all planning finishes before v0.1 then the clock only starts when the v0.2 work starts": the clock starts at the later of the plan-and-breakdown approval and the v0.1 tag, when the first v0.2 task is dispatched. Steps 1-6 (conversation, design spec, reviewer check, owner approval, plan with every coverage table, breakdown, owner approval) are planning and are not on the clock.
- Quality bar unchanged: the same gates, zero-bug rule, task and final reviews, mutation evidence, verifier pass. Speed comes from B, F and better planning only.
- Time use. The time-use targets of this build (TT) also apply to v0.2 and are reported daily. Until `gates timeuse` (section 7.5) lands they are measured the way this build measures them.

  | Share of agent-hours | Target |
  |---|---|
  | Writing code + reviewing | >= 35 % |
  | Running tests locally | <= 15 % |
  | Mutation tests locally | <= 3 % (after CI3) |
  | Waiting for test slots and CI | <= 8 % |
  | Waiting for owner answers | <= 5 % |
  | Coordinating | <= 20 % |
  | Gates, git, files and other tooling | <= 12 % |
  | Idle (usage limits, owner away) | <= 5 % |

  | Flow measure | Target |
  |---|---|
  | Agent runs ending BLOCKED: budget or checkpoint | < 5 % |
  | Controller start-up to first dispatch | median <= 5 min |
  | Fix rounds per task | mean <= 3 |
  | Findings first raised by a final review rather than a task review | < 20 % |

  A share outside its target on two days running is raised to the owner as a process question, with the cause and a proposed change (TT, "Tracking").
- Planned versus actual is tracked from day one.
- Spec stability: a spec change after approval is an owner question with its cause recorded. The count of such questions is the measure of anti-goal 3.

## 6. Stage B: findings and dispatch tool gaps

### 6.1 V2-06 and V2-07: who found a finding; loop statistics for inherited and pre-review findings

Source: notes, "V2-06 and V2-07 Who found a finding; loop statistics for inherited and pre-review findings (2026-11-26)"; owner: "yes go with that". Inventory V2-06 (TT:31), V2-07 (LG:1088, LG:1187; `gates/lib/loopstats.py:206`).

Current behaviour (inventory, checked on main): a finding record carries no review kind, so rework share and late findings cannot be measured. `loopstats` raises `finding <id>: review_round <k> is above --rounds <n>` (`gates/lib/loopstats.py:206`) for a finding moved into the task from another task (the v0.1 A4 fold rule produces these moves), so controllers compute the verdict by hand.

Behaviour as decided:

- Every finding record carries two fixed facts: `found_by` (`implementer`, `task_review`, `final_review`, `verifier`, `other`) and `found_in` (the task id and round where it was first raised). The owner field (`owner.task`) may move; these two never change. This is also V2-06 (review kind).
- `loopstats` counts only findings with `found_in.task` equal to the task and `found_by` a review of that task. Every other finding of the task is printed on a separate line, for example `carried in: 3 (4d.1 r5: LOW x3), pre-review: 1 (MEDIUM)`, and never enters X, W or the verdict (v0.1 §10, "Rules N and T").
- A task reaches CLEAN only when every carried-in and pre-review finding is fixed or registered against a named task (zero-bug rule): they cannot stop or prolong the loop, but they block the sign-off.
- The rework share and the late-findings measure come from the same facts: a finding first raised by a final review or verifier in code a task review already passed counts as late (target under 20 %).
- Rejected: counting carried-in findings at a lower weight (mixes two questions; arbitrary weights).

Interfaces:

- Finding schema: a new version (`finding/2`) adds `found_by` (enum of the five values) and `found_in` (`{task, round}`), with a migration from `finding/1` (v0.1 §15). The same version carries V2-01's `members` (section 7.1), so one migration covers both.
- `findings new` takes both facts (Builder's choice: flag spelling, for example `--found-by` and `--found-in <task>:<round>`); no command changes them after creation; `findings move` changes `owner.task` only.
- `loopstats` prints the separate line in the shape above: `carried in: <n> (<task> r<round>: <SEVERITY> x<count>, ...)` and `pre-review: <n> (<SEVERITY>, ...)`.

Edge cases:

- A moved finding whose `review_round` is above `--rounds` no longer makes `loopstats` refuse; it is not counted.
- A finding raised by the implementer, or by anything that is not a review of the task, is "pre-review".
- A finding carried in from a task with the same id prefix but a different task id is "carried in".

Builder's choice: which `found_by` values count as "a review of that task" for each loop of v0.1 §10 (the task fix loop counts `task_review`; for the stream fix loop that the verifier's report opens, v0.1 §10 "Verifier and merges" counts that report as review 1), stated in the plan and pinned by tests. How `loopstats` shows a blocked sign-off (for example a `sign-off: blocked by <ids>` line), bounded: it never prints CLEAN while a carried-in or pre-review finding is neither fixed nor registered against a named task. How "in code a task review already passed" is decided for the late-findings measure, bounded: from the record facts (`found_by`, `found_in`, cites) only. The definition of rework share, bounded: computed from `found_by` and `found_in` only, and stated in the `gates timeuse` docs. See open question OQ-1 for the facts of records written before `finding/2`.

### 6.2 V2-08: closing findings

Source: notes, "V2-08 Closing findings (2026-11-26)"; owner: "close it automatically once the fix merges and its test is pinned"; option (a) "computed, not written", "including the squash fallback and other 2 edge cases". Inventory V2-08 (LG:1151; `gates/lib/findings.py`).

Current behaviour (inventory, checked on main): the transition table lets `fixed-unpinned` go only to `pinned` (`gates/lib/findings.py:23`), and a pin needs a transcript; 0 of the 172 records on main are resolved.

Behaviour as decided:

- `findings.effective_status(record)` is the one function every reader uses: the register gate, `findings list`, the INDEX open findings, `loopstats` and `doctor`.
- It returns closed when (1) the record's fix commit is reachable from the base branch (one `git rev-list` over the base per run), (2) the pinned test exists on the base, and (3) the pinned mutation transcript exists and shows that test failing with the fix reverted. Otherwise: "fixed, waiting to merge" (fix not on the base) or "fixed, owes a test" (merged, no pin).
- From V2-01 (section 7.1): a finding cannot close until every member is resolved.
- The record file is not rewritten.
- Squash or rebase merges: when the fix commit is not on the base, the fix is accepted when a base commit carries the same patch (patch-id match) and the pinned test is on the base; otherwise the record stays "waiting to merge" and `doctor` flags it.
- A fix reverted later: the record still reads closed; the pinned test fails in CI, which catches the regression as a new finding.
- Records with no pin (most of today's open ones) show "fixed, owes a test" until pinned; nothing is closed silently.

Interfaces:

- `gates/lib/findings.py`: `effective_status(record)` (Builder's choice: how the one `git rev-list` per run is shared across calls, for example a context object built once per run and passed in; the signature in the notes is the record only).
- `python3 -m gates findings list` (new subcommand; v0.1 §7.3 has `new` and `move`): prints each record with its effective status. Builder's choice: columns and `--json` shape.
- `doctor`: a line per record that stays "waiting to merge" because no base commit carries its patch.

Edge cases:

- The base has the fix commit but not the test: "fixed, owes a test".
- The test and transcript are on the base but the fix commit is not and no patch-id matches: "fixed, waiting to merge", flagged by `doctor`.
- More than one base commit carries the same patch id: Builder's choice, bounded: any match accepts, and the matching sha is printed.
- `gate_register` reads the effective status, so a record that is closed by computation counts as resolved wherever v0.1 §7.2 reads "resolved" (immutability, the no-delete rule, the cleanup's deletion proof).

Builder's choice: which field names the fix commit (an existing `history` entry or a new `finding/2` field, which then lands in the same schema version as section 6.1); the machine values of the two fixed states in `--json` (the display text is the notes' wording); what `effective_status` returns for the states before a fix (`open`, `planned`, `in-progress`, `deferred`), bounded: their written status, unchanged. The patch-id form (for example `git patch-id --stable`), bounded: it works on git 2.30. See open questions OQ-2 (how "the pinned test exists on the base" is checked stack-neutrally), OQ-3 (the transcript when mutation results come from CI, and the light profile) and OQ-4 (whether any step still writes `merged`).

### 7.5 V2-05: `gates timeuse`

Source: notes, "V2-05 gates timeuse (2026-11-26)"; owner: "yes that matches, go ahead". Inventory V2-05 (LG:1191; TT:3).

Behaviour as decided:

- Reads the project's local Claude Code transcripts only (never sent anywhere), with the rules of this build's `timeuse.py`: tool calls timed and categorised, model turns attributed by role, controller waits on children not double-counted, suspended time counted as idle.
- `python3 -m gates timeuse [--day YYYY-MM-DD | --since ...] [--json]` prints the agent-hour shares and the flow measures (budget endings, controller start-up, fix rounds per task, late findings from V2-06).
- Optional `timeuse.targets` in config: a share outside target prints WARN, never fails a gate.
- One time-use line in each checkpoint/handoff; the program status page shows the latest shares; two days outside target is suggested as an owner process question.
- An unrecognised transcript shape prints "transcript format not recognised" instead of numbers. The HTML pie page stays this repository's local convenience.

The reference rules, as this build's `timeuse.py` and `timeuse_flow.py` apply them (program folder, untracked):

- A model turn's time is the gap since the previous record, attributed to the role named on the transcript's `## Role` line (implementer roles to writing code; reviewer, verifier and investigator roles to reviewing; drafter and plan writer to planning; controllers to coordinating); a gap over 15 minutes is idle.
- A tool call's time runs from its use to its result, categorised by tool and, for Bash, by command; a call that starts a background job, or an Agent call, adds nothing (the child's own transcript counts its time); a controller's poll of a child's output is not counted (no double count).
- A call longer than its kind allows (4 hours for test and mutation runs, 45 minutes otherwise, none for owner questions) is cut there, and the excess is idle.
- The flow measures: how agent runs ended (from the report status in the last records), the controller's time from start to its first Agent call (median), fix rounds per task, and the late-findings share (section 6.1).

### 10.15 V2-49: the clean-update rule

Source: notes, "V2-49 Clean-update rule in the spec (2026-11-26)"; owner: "yes that matches, go ahead". Inventory V2-49 (PL:52, PL:8085 Q-SPD-4 (a)). LS A1 (delta final review) is v0.1.

The rule, in full, as the v0.2 spec states it (it lands in v0.1 §8a as a new item after "Dependency skips"):

- A clean update needs only the gates re-run. An update is clean when: there is no conflict; no changed path is shared with the PR; no module named in the PR tasks' Consumes lines changed; the gates pass on the merged head.
- A conflict in test literals only, each resolved as the exact union, needs a short review of the merge plus CI.
- Anything else needs a delta final review (A1).

The mechanics, from the v0.1 plan (owner 2026-11-10; PL:52): the branch takes the base by `git fetch` and then `git merge --no-commit --no-ff origin/main` in its worktree, as its own command. With `B` the branch head before the merge, `O` the paths of the PR's own diff (`git diff --name-only --no-renames origin/main...B`) and `M` the paths the merge changes in `B` (`git diff --cached --name-only --no-renames B`): no conflict means exit 0 and `git diff --name-only --diff-filter=U` empty; no shared path means `M` and `O` share none; the Consumes condition reads `M` against every module a `Consumes:` line or an "Interfaces consumed" list of the PR's tasks names. The ledger gets the `UPDATE` line and a `Clean update:` line naming head, reviewed head and the counts.

The delta final review (LS A1): "after an update from main, the final review covers the update diff, the main changes to consumed modules and how the PR uses them, and a full suite on the new head. A fresh whole-PR review only when the PR's own code changed beyond reviewed fix diffs."

Builder's choice: the base-branch name in the command comes from config `base_branch` (v0.1 §6), not a literal `main`. See OQ-11 (the plan's fourth condition, skip dependencies, which the notes do not list).
