# Base playbook: review

How work is reviewed and verified, how the fix loop runs and when it stops. The mutation review (row `SD-R10`) and the clean-copy review (row `SD-R9`) are rules of `playbook/rules.md`, not text here.

## Task review

A `task_reviewer` judges one task's diff. Reviewers execute every claim and re-run every gate themselves, on a clean copy of the reviewed head (row `SD-R9`); before a review the controller trial-merges the branch with the base branch and runs the test modules of the changed files, plus every test module that imports a changed module, on the merged tree, on every supported runtime; the full suite runs on the head of each pull request, at a stream's end before its adversarial review (where the profile enables it, strict), and in that review. On a fix round the reviewer checks the fix diff against the fix rule ("Fix loop") and tests any blame on the fix commit's parent and on the fix commit. A reviewer has no out-of-scope bucket for the task's own code: one defect the change caused goes in findings, one it did not cause goes under Unrelated findings with file:line, a reproducer and its class statement, and gets a register row and an owner. A cosmetic item (a dash, a space, wrapping, wording with no change of meaning) is not a finding: the reviewer marks it cosmetic, and it is noted, folded into the next real edit, or dropped. The report is DONE when every claim and gate re-ran clean and the task's diff holds no finding.

## Final review

Before a pull request opens, a `final_reviewer` reviews the whole branch against the base branch, not one task: every commit, the sum of the diff and the seams between tasks. A block ends with this review on its stream branch. A block whose code another stream consumes, through an edge in the breakdown, opens its pull request as soon as it is ready, after this review; a block no other stream waits on stays on the stream branch and goes out with the stream's final pull request. The review checks that each task's claims were true at the commit that made them and are still true at the tip, that no later commit undid an earlier fix, and that the branch matches the plan section it was built from. An update from the base branch after this review is reviewed as a delta: the merge's diff, the base branch's changes to the modules the branch's tasks consume and the branch's uses of them, and one full suite on the new head; a fresh review of the whole branch runs only when the branch's own code changed beyond reviewed fix diffs. A branch ends in this order: final review, the full suite on the pull request's head, the top-tier verifier and the review of its fix diffs (at a stream's end only), the owner's approval, merge, post-merge gates, checkpoint. The top-tier verifier runs only where the profile enables it, the strict profile (design spec section 12); the light and standard profiles skip that step.

## Verifier

Once per stream, at its end, after a clean final review and where the profile enables it (strict), the `final_verifier` tries to break everything the stream delivered, the parts it already merged included; a plain plan counts as one stream. It runs at the top tier, `tier4`, which only the `top_tier_roles` use (or at the configured `top_tier_fallback` when the project sets no `tier4`). It runs once, not for each block or each pull request, and it is not re-run after the fixes its findings cause: those fixes get a review of their diff ("Fix loop"). A defect it finds in already-merged code is fixed in the stream's final pull request or in a small follow-up pull request. It assumes the reviewers missed something: it runs every gate, the full suite and the test command itself on every interpreter the brief names, runs the suite with `GIT_*`, `TZ` and `LANG` polluted, and feeds each gate and check inputs from outside its whitelist, at the edges of every input-domain row, and in the combinations no single task covered. Its report is DONE only when it could not break the change.

## Fix loop

Zero bugs: a change's own bug makes it incomplete. A minor is a real defect: it is fixed, or registered as a LOW under LOW_PLATEAU, or registered against a named task when the binding verdict (STOP_NARROW, ESCALATE) stops the loop, and otherwise never deferred. A cosmetic item is not a finding and earns no fix round. A document re-review reads the whole document and is stopped by the same binding verdict ("Plan review"). A deleted test is restored and fixed; dropping a test is never offered as a fix. A class of findings is an epic with child rows, signed off only when every child is resolved and the whole class is tested and reviewed. A finding's class statement lists every member a search of the code finds, with the search recorded; the fix tests each member, and a re-review first runs the search again and reports a missing member as a finding.

Each finding goes back to the implementer with its class quoted verbatim, and every fix is re-reviewed, scoped to the fix diff plus the finding's dimension. Fix rounds 1-3 resume the implementer; rounds 4-5 go to a fresh agent one tier up; the re-review of round 5 is review 6, and the Rules N and T verdict ("Rules N and T") then stops the loop at `k > 5` ESCALATE: the open LOW and MEDIUM findings are registered against a named follow-up task, and an open CRITICAL or HIGH finding becomes an owner question that blocks only that task, never the stream. STOP_NARROW also stops the loop: the open findings are narrowed in one last round or registered for a planned task ("Fix rule"). For the LOW and MEDIUM findings either verdict leaves to register, the owner question on which task takes them recommends a planned task of the same stream whose files include a path the findings name, and a new task only when no such task exists or the fix is too large for that task. The report of the stream-end adversarial review counts as review 1 of its loop, and each review of a fix diff counts as the next review; a CRITICAL or HIGH finding is always fixed, and the stream's final pull request does not merge while one is open. A small re-review may run below the reviewer's minimum tier ("Small re-review").

Fix rule. A fix round's diff may only narrow (refuse the bad input, so the code fails closed) or correct existing behaviour to what the plan already says. It may not add new modelled behaviour: no new branch that re-implements another system's rules (a parser, a shell, a library's error text, a file system's semantics). A fix diff passes when every branch it adds or changes either refuses input with a named error, failing closed, where the code previously accepted or crashed, or makes behaviour match a plan or spec sentence that the fix report quotes; it fails when a branch newly accepts input the code used to refuse, or reproduces another system's behaviour that no quoted plan or spec sentence requires. A finding whose resolution needs new behaviour is first narrowed in the fix round, so the input is refused and the code is safe; a register row then names a proposed new task with its own input-domain table, and adding it to the plan is a plan change the owner approves (`scope`), which blocks only that task. The reviewer checks every fix diff against this rule and applies the test; a violation is itself a finding, and on a disagreement the controller rules and logs `Decision (controller)`. Blame is tested: a finding labelled as caused by the fix, or by a round, counts as such only when its reproducer passes on the fix commit's parent and fails on the fix commit, and the reviewer records both runs; otherwise the finding is pre-existing, still handled, and not counted against the fix. After a fix the dimension is re-checked; widening the behaviour is out of scope for a fix.

LOW_PLATEAU: after two consecutive reviews whose change-caused findings are all LOW (a review with no change-caused finding counts as all-LOW), the loop ends and those LOWs are registered against a named follow-up task instead of being fixed, and the work moves to the final review. A review with no change-caused finding at all is clean, so LOW_PLATEAU ends the loop at a review that holds LOW findings, after a review that held only LOW findings or none. A change-caused CRITICAL or HIGH finding is always fixed, whatever the verdict says. Until `python3 -m gates loopstats` exists, the controller applies the verdict and the weighted tally by hand and ledgers the verdict.

## Input domains

The input-domain method binds every task, plan and review:

1. Every task whose interface takes an argument or reads a file carries an input-domain table in its brief, copied from the plan's input-domain dimensions: sections per producer, columns `# | dimension | values | expected verdict | test`, one row per parameter or filesystem call and dimension (argument type, subclasses and bool as int, path kind, character class, the character after each indicator, each output position, the resources held on each error path), an Oracle section and a section of the binding owner rulings. A missing table blocks dispatch; a row with no test is a finding, and its fix re-checks the whole dimension without widening the behaviour ("Fix rule"). A table enumerates the full input class or restricts the input, so the code refuses what lies outside the enumerated class, and never samples an open grammar. Every table carries rows for the known version differences of the project's own stack and runtime, each run on every runtime the project supports.
2. The oracle is the production path compared with an independent expected value, never one read back from the code under test.
3. An implementer lists every behaviour the brief does not state and every knowing divergence, and stops with NEEDS_DECISION. In a fix round it first lists the invariants the replaced code held and tests each. It writes one mutant per changed production condition or call.
4. Reviewers have no out-of-scope bucket for the task's own code. A class that seems to exclude a failing whitelist input is a class-narrowing question for the controller, which rules under the fix rule and logs `Decision (controller): class -- action -- cost if wrong`; the owner is asked only when the resolution changes shipped user-facing behaviour, the spec or scope (`spec-direction`, `scope`), or on ESCALATE with an open CRITICAL or HIGH finding. A missing table is a finding.
5. Each finding's class is written by input dimension, `class: <dimension>: <members>`, and fix and re-review dispatches quote it verbatim.

A mismatch a table finds is a controller ruling only inside an approved plan, and only when it is a plan-vs-spec or task-vs-task conflict the spec settles; any other mismatch, plan-vs-code included, is an owner question, except a small point that `playbook/decisions.md` ("Asking") lets the controller decide.

## Small re-review

The config key `reviews.small` sets the small re-review. A re-review of fix round 1 to 4 of one task by `task_reviewer` may run at the tier `reviews.small.tier` names (default `tier2`) instead of the role's minimum tier when every condition holds (the rule lowers the tier only where the role's minimum tier is above `reviews.small.tier`; `task_reviewer` is tier2, so at the default it lowers nothing):

1. It is scoped to that fix's diff, not a full re-review.
2. The fix diff has at most `reviews.small.max_lines` changed lines in at most `reviews.small.max_files` files.
3. No changed path matches `reviews.small.exclude`.
4. The findings the fix answers are LOW or MEDIUM only, and no owner question is open for the task.
5. The previous review found no defect caused by a fix.
6. Rule N does not fire.
7. From review 3 on, Rule T converges (`p <= 1/10` with a finite remainder `R`).
8. From review 3 on, with `escape_cost` set, the expected-value figure is below one round.

"From review 3 on" means once the task has had three reviews, so from the re-review of fix round 3; before that, conditions 1-6 decide. Rules N and T are computed over the reviews done before the re-review being dispatched. The dispatch states the conditions on one `small-re-review:` line of `## Brief`. The dispatch check admits the lower tier only when the conditions it can check from git, the finding records and `loopstats` hold (1-3, the severities of 4, and 6-8); the controller's `small-re-review:` line states the rest (no open owner question in 4, and 5), which the small re-reviewer checks. A small re-reviewer must escalate on any defect it finds, on NEEDS_DECISION and when it is unsure, and the next re-review then runs at the role's minimum tier; the re-review of fix round 5 always runs at it.

## Process-defect stop

Findings that keep arriving round after round are a process defect. The controller does not start another fix round: it must stop fixing, find where the findings entered and why reviews missed them, and bring process changes to the owner.

## Rules N and T

After each review the controller runs `python3 -m gates loopstats` (by hand until it exists, "Fix loop"), which prints the signals Rule N (novelty) and Rule T (trend) and, when `escape_cost` is set, an expected-value verdict, and ledgers its `Loopstats:` line (`Loopstats: <task> r<k>: X=<...> p=<p> q=<q> nu=<nu> -> <VERDICT>`). The verdict is binding: it decides when the fix loop stops ("Fix loop"), and it never stops a change-caused CRITICAL or HIGH finding from being fixed. The other signals only decide whether a re-review may run below the reviewer's minimum tier.

A finding carries `review_round`, `caused_by_change` and `dimension`. After each review, before `loopstats` runs, a finding record (schema `finding`) is written for each finding of that review, with `python3 -m gates findings new --review-round <k> --caused-by-change yes|no --dimension <dimension>` (plus its required flags), under config `paths.findings` on the task's branch, by the controller, which mints each id with `findings new` (owner answer Q-PV2-3 (a), 2026-11-17). The records stay on that branch while its pull request is open and merge with it, and `loopstats` counts only findings that have a record. For one task after `k` reviews, the counted findings are those the task's change caused (`caused_by_change: true`) with severity CRITICAL, HIGH, MEDIUM or LOW; `X_i` is the number from review `i`. Rule T counts a severity-weighted tally: a counted finding weighs 8 (CRITICAL), 4 (HIGH), 2 (MEDIUM) or 1 (LOW), `W_i` is the sum of the weights of review `i`'s counted findings, `N = sum W_i` and `S = sum (i-1) W_i`, so each finding counts as that many draws in the exact test and in the fit.

- Rule T: `p = P(S' <= S)`, where `S'` is the sum of `N` independent uniform draws on `{0..k-1}`, computed exactly; the trend is converging at `p <= 1/10`. A truncated-geometric fit (`q` with `sum j q^j / sum q^j = S/N` over `j = 0..k-1`) gives `a = N/(1-q^k)`, the remainder `R = a q^k` and the expected next-round count `E_next = a(1-q) q^k`; at `S/N >= (k-1)/2` the fit is at its boundary, `R` is unbounded and `E_next = N/k`.
- Rule N: the novelty `nu` is the share of review `k`'s counted findings whose `dimension` (one canonical dimension from the input-domain table's row names, given by the reviewer) is on no counted finding of an earlier review; Rule N fires when `k >= 2`, `X_k > 0`, `nu >= 1/2` and `X_k >= X_(k-1)`. A narrowing of the contract is noted and counted, never a reset.

The verdict, in order: `X_k = 0` CLEAN; LOW_PLATEAU when the LOW run, the consecutive reviews ending at review `k` whose counted findings are all LOW (a review with no counted finding counts), is at least 2, so, since CLEAN comes first, LOW_PLATEAU fires only at a review `k` holding LOW findings, after a review that held only LOW findings or none ("Fix loop"); `k > 5` ESCALATE; Rule N fired: STOP_NARROW, or ESCALATE after a narrowing; `k < 3` CONTINUE; converging and the fit not at its boundary: CONTINUE; otherwise ESCALATE after a narrowing, else STOP_NARROW when `nu >= 1/2`, else ESCALATE. With `escape_cost` set, the expected-value figure is `E_next * sum_s (n_s/N) * escape_cost[s]`, `n_s` the number of counted findings of severity `s` over all reviews (`E_next` and `N` are the weighted tally's, so `E_next/N` is the expected next-round share of it); it reads `continue` above one fix round, else `stop`, and never changes the verdict. STOP_NARROW and ESCALATE stop the loop and their open findings are handled as "Fix loop" says. A CRITICAL or HIGH finding the change caused is fixed whatever the verdict.

## Review methods

- Test first: a new test is watched red for its stated reason, re-established with a behaviour stub, not only a missing import. When tests came after the code, the red check overlays the new tests on a clone of the pre-change commit.
- Evidence: an input outside a whitelist fails closed with a named check; a divergence is reported with both quotes and no side taken; a pasted result is re-run before it is relied on.
- No claim is trusted: each is verified directly and by contradiction, and both commands are recorded.
- Pinned means a production-path test plus a mutation transcript; the mutation review (row `SD-R10`) and the clean-copy review (row `SD-R9`) run as `playbook/rules.md` states them.

## Plan review

A review of a plan or a spec edit checks:

- every prose quote of 12 or more characters is verbatim in its source, by a whitespace-normalising script re-run after each edit;
- each edit's old text occurs once at HEAD, and its new text occurs once after the edit;
- every `Consumes` name matches the code or an earlier `Produces`;
- owned paths are pairwise disjoint (a trailing `/` means everything under it);
- a sub-block holds at most `block.max_tasks` tasks, each in the full task shape with an executable check that asserts;
- no placeholder (`TBD`, `TODO`) remains;
- an omission is reported as an omission, not as a contradiction.

A plan, spec or breakdown re-review is stricter than a code re-review and bounded by the same math:

- a re-review reads the whole document, because it is the source of truth; an edit corrects only what was flagged and adds no new design (the fix rule for documents);
- the Rules N and T verdict stops the loop; when it stops, the open LOW and MEDIUM findings are fixed in one final edit pass, not registered, and an open HIGH or CRITICAL finding is always fixed; if ESCALATE leaves one open, it goes to the owner, who is involved in planning anyway;
- one adversarial review runs at the end of planning, over the spec, plan and breakdown together, before the owner approves the plan;
- after approval, plan text changes only through the plan-change path, and a finding in implementation never reopens the planning loop.
