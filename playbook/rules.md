# Base playbook: rules

These are the base rules of the strict-delivery framework; each row gives the rule, why it holds, what enforces it, the profiles it applies to, whether it is fixed and its source in the design spec. A `fixed: yes` rule (owner-only classes, merge grants, the bypass block) is never overridden. Any other rule is overridden only by a project decision of class `rule-override` that carries the optional field `overrides: SD-R<n>` (decision schema `decision/2`), and a decision whose `overrides` names no rule in this table is refused. The SessionStart hook lists the active overrides, and project rules live in `.strict-delivery/playbooks/`.

| id | rule | why | enforced by | profiles | fixed | source |
|---|---|---|---|---|---|---|
| SD-R1 | Every change, of any size, is a register row before work starts. | Work with no row has no owner and no review trail. | gate_register | light, standard, strict | no | spec §8 |
| SD-R2 | No claim is trusted: each one is verified directly and by contradiction, and both commands are recorded. | A claim checked one way can be wrong in the way that check cannot see. | gate_claims | standard, strict | no | spec §8 |
| SD-R3 | Owner-only classes are questions in the decision log, and the path halts until the owner answers. | Only the owner decides these classes, so an agent never assumes the answer. | gate_decisions | light, standard, strict | yes | spec §8 |
| SD-R4 | Report before plan: after an audit the owner rules on triage before any plan, and no plan the owner has not seen is committed. Every block of a spec and its plan is planned in full (tasks, files, interfaces, input-domain dimensions, tests) before any code is written, every test step carries its assertions as code, and no block whose plan is only an outline starts implementation. The last planning step is the stream breakdown, `<paths.plan_state>/<plan>/breakdown.yml` (kind `breakdown/1`, spec appendix A): the streams with their owned paths, the tasks of each stream, the dependency edges from task to task, each stream's unblock condition, the parallel groups (each within the concurrency limit), the concurrency and depth limits it assumes, the tasks already done and, for ownership that moves during a program, stream periods and path windows; streams run as they unblock. Each kind of change has its superpowers skill: a new rule, feature or format with no settled design goes through superpowers:brainstorming to an owner-approved design and then a spec edit, a plan change through superpowers:writing-plans against the spec, and execution through superpowers:subagent-driven-development or superpowers:executing-plans under the strict prompt blocks. A controller that has not invoked the skill for the change in its current context dispatches no writer for it. When a program starts, `program create` refuses a plan with an outline-only block (a block section without task headings, or a pointer to a section that does not exist or holds none), a plan without the expected block structure, or a missing or invalid breakdown: one whose `max_concurrent` or `max_depth` exceeds the effective limit (the lower of config `limits` and the measured Claude Code limits, spec §10), or whose streams, owned paths (with their windows) or stream periods differ from the program's `streams.yml` (programs and streams design §5). | Code written against an unseen plan or an outline builds what nobody approved. | program create (programs); judgment | light, standard, strict | no | spec §8 |
| SD-R5 | Zero bugs: a change's own bug makes it incomplete, and a minor is a real defect, fixed in the fix round and never deferred. A cosmetic item (a dash, a space, wrapping, wording with no change of meaning) is not a finding and earns no fix round: the reviewer marks it cosmetic, and it is noted, folded into the next real edit, or dropped; a document re-review runs in full until a clean pass. An unrelated bug gets a register row and an owner. | A deferred defect is a defect shipped. | judgment | light, standard, strict | no | spec §8 |
| SD-R6 | A deleted test is restored and fixed; dropping a test is never offered as a fix. | Removing the test hides the failure without removing its cause. | judgment | light, standard, strict | no | spec §8 |
| SD-R7 | A class of findings is an epic with child rows, signed off only when every child is resolved and the whole class is tested and reviewed. | Fixing one member of a class leaves its siblings broken. | judgment | light, standard, strict | no | spec §8 |
| SD-R8 | Findings that keep arriving round after round are a process defect: stop fixing, find where they entered and why reviews missed them, and bring process changes to the owner. | More fix rounds cannot repair the step that lets the defects in. | judgment | light, standard, strict | no | spec §8 |
| SD-R9 | Reviewers execute every claim and re-run every gate themselves, on a clean copy of the reviewed head: a `git archive` export or a detached worktree, with `pwd -P` and `git rev-parse --show-toplevel` checked inside it and no tracked file flagged assume-unchanged or skip-worktree (`git ls-files -v`). Before a review the controller trial-merges the branch with the base (`git merge-tree`) and runs the full suite on the merged tree. The verifier runs the suite with `GIT_*`, `TZ` and `LANG` polluted. | A result seen only in the author's checkout can depend on that checkout's state. | judgment | light, standard, strict | no | spec §8 |
| SD-R10 | Pinned means a production-path test plus a mutation transcript. A mutation review writes one mutant per changed condition and runs each on a fresh `git archive` export or private clone, never the checkout, after a syntax check of the mutated file, in three runs (present, mutant, restored). Every surviving mutant is argued equivalent or is a finding, and a mutant count with no script or transcript on disk is a finding. | A test that no mutant fails does not show that the fix is needed. | gate_evidence | standard, strict | no | spec §8 |
| SD-R11 | One block per agent context, at most `block.max_tasks` tasks, and a clean worktree at every checkpoint; `gate_checkpoint` counts a block's tasks both as its plan's `Task <block>.<n>` headings and as the distinct `<block>.<n>` task tokens of its ledger's `CHECKPOINT` lines. Continuation is automatic: an agent that reaches a checkpoint, 80 % of its token or time budget, or a usage-limit stop writes its handoff and returns, and its dispatcher at once dispatches a fresh agent of the same role with a continue prompt built from the handoff, ledger and status page. Nothing continues from inherited memory, and the owner never runs `/clear` and re-prompts. A checkpoint rewrites the handoff with the handoff fields of spec §9, commits handoff and ledger after the commit gate and writes the `CHECKPOINT` line. A statement that a handoff is complete carries the output of `git status --porcelain --untracked-files=all`, the handoff field check (`gate_checkpoint`) and the background-job check below. Nobody says "safe to clear", since nothing is cleared at any level. | A long context drifts from the plan, and only a written handoff carries the state to a fresh agent. | gate_checkpoint | standard, strict | no | spec §8 |
| SD-R12 | The base branch is protected: nothing is pushed or merged to it directly. Every change reaches it by a pull request on all-green, merged by merge commit on the owner's approval: in `controller` mode the owner approves in chat naming the PR and its head sha and the controller runs `gh pr merge --merge --match-head-commit <sha>`, and in `host` mode the owner merges on the host. The plan's ledger records each merge as a `MERGED` line, and merge approvals are not decision records. Work branches (stream, block and group branches) are pushed at every checkpoint (`gate_checkpoint`'s `checkpoint.pushed`), and the program controller pushes `<program>/integration` after every commit it makes there. Two merges need no approval: a stream controller merging a group branch into its stream branch after a clean review and green gates, and the program controller merging main into the integration branch and into each stream branch behind it during a sync, never rebasing. If such a merge conflicts, the controller stops and asks the owner. | Only the owner lets work into the base branch, and pushed work branches survive a lost machine. | hook | light, standard, strict | yes | spec §8 |
| SD-R13 | After a merge, and at a program's close, the cleanup step removes the per-effort files from the tree in a pull request of its own (spec §5); evidence cites them as `<sha>:<path>`. | Per-effort files would otherwise pile up in the tree, while their history stays citable. | gate_cleanup | light, standard, strict | no | spec §8 |
| SD-R14 | Every agent reaps its background jobs before reporting: a poll loop has a bounded timeout and never matches its own command line, a job no longer needed is stopped with TaskStop and never by pattern-killing processes, and the report lists each background job id as finished or stopped. The controller checks for orphans: before ledgering an agent's result it lists the agent's background job ids from its transcript, and each has a completion record or is stopped with TaskStop and the stop is ledgered. A notice that an agent is waiting on its own background work leaves its task open. | An orphaned job keeps changing files after its result was accepted. | judgment | light, standard, strict | no | spec §8 |
| SD-R15 | Scripts that write files start with `set -eu` and assert they run inside their scratch path. Every agent works in its own `mktemp -d` scratch path, never a shared scratchpad, and never runs `git stash` in a shared checkout; a reviewer checks `pwd -P` and `git rev-parse --show-toplevel` inside its clone before it writes. In the commands they run (shell lines and inline scripts, not the code they write), agents use no heredoc, no `rm`, `rmtree` or `os.remove`, and no `$(...)` except around `mktemp`. These rules bind every agent, the main session included; a worker discloses a slip in its report, and the main session discloses its own in the ledger. | A shared scratch path, a stash or a stray delete destroys another agent's work. | judgment | light, standard, strict | no | spec §8 |
| SD-R16 | Owner rules go into decisions, rolled into playbooks, CLAUDE.md or `architecture.md`; agent memory only points to them. | Memory belongs to one agent on one machine, while the decision log is shared and checked. | judgment | light, standard, strict | no | spec §8 |
| SD-R17 | Dispatch only inside the role/model map; the top tier only for `top_tier_roles`. | A role run outside its tier changes the quality or cost the owner chose. Wherever a program is live, `gate_dispatch` runs, whatever the profile. | gate_dispatch | standard, strict | no | spec §8 |
| SD-R18 | The bypass block of the PreToolUse Bash hook refuses, in every profile, an agent's `--no-verify` and its abbreviations, `-n` on `git commit`, `core.hooksPath` in any case, `git -c` and `--config-env`, `GIT_CONFIG_*`, and moves of `HOME` or `XDG_CONFIG_HOME`. | A gate an agent can skip enforces nothing. | hook | light, standard, strict | yes | spec §4 |
| SD-R19 | Production-path: a test drives the real code path, not a mock of it, and whether it does stays a reviewer's judgment, worded the same whatever the stack or test tool. | A test of a mock proves the mock. | judgment | light, standard, strict | no | spec §13a |
